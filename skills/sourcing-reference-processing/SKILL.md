# 기존 업로드 상품을 참고한 상품 가공

## 1. TRIGGER
- 선택한 상품을 기존 업로드 상품과 비슷한 형식으로 가공하라는 작업에 사용한다.
- 참고 상품 조회만 요청되면 조회·비교까지 수행한다. 에이전트 생성이나 스킬 배정만으로 전체 상품 일괄 가공을 시작하지 않는다.
- 상품 수집, 쇼핑몰 등록·동기화, 판매가격 변경, 주문·배송 작업으로 확대하지 않는다.

## 2. GROUND
- 상품 가공 운영에서는 주입된 도구로 프로젝트·원본·현재 상품을 확인한다. 코드 개발용 문서 정비나 무관한 Space 검색을 가공의 선행 조건으로 만들지 않는다.
- 가공 전 상품은 `list-sourcing-workspace(stage=unprocessed)`로 확인한다. 공통 편집본 목록이 비어 있다는 이유로 원본이 없다고 결론 내리지 않는다. 선택한 원본에 `start-managed-processing`을 호출하고 반환된 공통 상품 ID로 편집한다. 도구가 없으면 스킬 배정과 플러그인 연결·도구 권한을 구분해 원인을 보고한다.
- 할당된 작업에서 회사·프로젝트·대상 상품 ID와 가공 범위를 확인한다. 기존 `sourcing-product-processing` 스킬의 원본·SKU 보존 절차를 함께 따른다.
- 먼저 [도구 호출](references/tools.md)의 실행 도우미로 운영 플러그인의 실제 도구와 스키마를 조회한다. 현재 실행에 주입된 인증을 사용하는 native API가 기본 경로다. MCP의 승인 오류를 도구 부재로 판단하거나 같은 검색을 반복하지 않는다.
- `list-managed-products`의 `view="uploads"`로 등록 상품을 읽고, 유사한 상품은 `get-managed-product`로 상세 설명과 SKU를 확인한다. 반환된 한 페이지를 전체 카탈로그라고 말하지 않는다.
- [참고 형식](references/style.md#참고-상품-찾기)의 `reference-profile.mjs`로 등록 상품을 순차 조회한다. 원본에서 확인·번역한 상품 종류와 한국어 검색어를 전달하고, 반환된 상위 후보의 실제 용도·옵션을 검토해 참고 상품과 이유를 선택한다. 카테고리만 같은 상품을 같은 종류로 판단하지 않는다. `catalogComplete=false`이면 조회한 범위만 기록한다.
- 사용자가 지정한 참고 상품을 우선한다. 지정하지 않았으면 상품 종류·사용 목적·옵션 축이 가까운 사례를 고르고 선택 이유를 기록한다. 관련 사례가 없으면 무관한 상품의 사실을 가져오지 않는다.
- 대상 원본과 참고 상품을 구분한다. 대상 SKU ID, 순서, 숫자·단위, 가격, 카테고리, 쇼핑몰 연결과 최신 revision을 확보한다.
- `get-processing-source`로 편집 전 원본 SKU·옵션·이미지와 sourceHash를 확보한다. 같은 프로젝트 쇼핑몰의 `accountId`를 사용하며, 가공 시작 후 재실행에서도 원본을 다시 읽는다. 이미 가공된 편집본을 원문으로 취급하지 않는다.
- 신규 카테고리를 정할 때 `list-product-stores`에서 현재 프로젝트의 활성 쿠팡 쇼핑몰을 선택한다. `recommend-coupang-category`로 후보를 받고 `get-coupang-category-metadata`로 필수 옵션·고시·인증·서류를 조회한다. 추천 실패나 사실 근거 부족을 참고 상품 복사로 대신하지 않는다.
- 이미지 상태는 `get-image-processing-jobs`로 읽고 [서버 이미지 처리 절차](references/higgsfield.md)를 읽는다. 기본 자동 누끼는 로컬 BiRefNet이며 에이전트에는 원격 MCP를 추가하지 않는다.
- 이미지의 내용은 실제 이미지를 열어 확인한다. URL이나 파일명만으로 색상·재질·치수를 판단하지 않는다. 추가 확인이 필요할 때 사용 가능한 Aside의 계정·기존 탭을 확인하고 읽기 작업에 사용한다.

## 3. DECIDE / PLAN
- '가공해줘'는 편집본 저장에서 끝내지 않고 상품명·전체 SKU·사용 이미지·상세 설명·카테고리의 실제 결과까지 검증하는 작업이다. 먼저 대상별 완료 조건과 이미지 목록을 만든다. 대표·SKU·최종 상세에 쓰는 모든 고유 이미지를 포함한다. 가공에 필요한 자료와 게시 단계에서만 필요한 가격·인증·공개 호스팅 사실을 구분한다.
- 처음부터 다시 가공할 때도 수집 원본을 다시 읽고 현재 편집본과 대조한다. 이전 보고서를 정답으로 복사하거나 기존 편집본·원본·SKU·첨부 이력을 초기화하지 않는다. 이전 글자 제거 결과가 불합격이면 최초 원본을 입력으로 교정한다.
- 짧은 가공 기준을 만든다: 참고 상품과 이유, 상품명 구성, 옵션 표시 규칙, 대표 이미지, 상세 설명 순서, 확인할 사실과 미지원 도구.
- [참고 형식과 적용 기준](references/style.md)을 시작점으로 사용하고 대상 상품의 근거에 맞게 조정한다. 참고 사례의 잘못된 속성명·중복 구간까지 따라 하지 않는다.
- 공통 상품 편집은 `get-managed-product` → `save-managed-product`를 사용한다. 해시가 검증된 수집 원본의 별도 초안은 발견된 processing 도구를 사용한다. 두 객체의 ID·revision·완료 조건을 섞지 않는다.

## 4. EXECUTE
- **상품명:** 주요 상품 종류 → 근거 있는 용도·특징 → 구분에 필요한 옵션 순서로 자연스러운 한국어 이름을 만든다. 반복 검색어를 줄이고 모델·브랜드·인증·효능은 원본에서 확인된 것만 사용한다. 상품명은 100자 이내로 저장한다.
- **참고 형식 적용:** 참고 상품명에서 상품 종류·용도·특징의 순서와 검색 표현을 파악해 대상의 사실로 다시 작성한다. 옵션 앞의 수집 내부 번호는 표시 이름에서 제거하되 실제 SKU ID는 보존한다. 비어 있는 옵션 축은 새 값으로 채우지 말고 가공 대상에서 제외한다. 서로 다른 원본 구매 조합을 같은 이름·옵션 조합으로 합치지 않는다. 상세의 옵션 안내는 한 번만 만들고 실제 판매 SKU와 같은 순서로 이미지·규격을 배치한다. 참고 HTML 전체나 다른 상품 이미지·가격·고시를 복사하지 않는다.
- **옵션:** 모든 대상 SKU와 구매 조합을 유지한다. 원본의 치수·수량·호환성·색상 차이를 빠뜨리지 않는다. 숫자의 단위를 추정하지 않는다. 옵션 이름과 값은 실제 카테고리 속성에 맞추고, 등록 상품의 속성 변경은 API에서 허용되는 범위를 확인한다.
- **구매·사용 제한:** 원본의 금지, 제외, 비호환, 주의 조건을 SKU별로 대조해 옵션과 상세 설명에서 같은 강도로 유지한다. 구매 금지를 비권장으로 약하게 바꾸거나, 구매 제외 안내를 물리적 사용 불가·의료 안전 보증으로 확대하지 않는다. 잘린 원문은 확인된 부분만 번역하고 누락을 기록한다.
- **이미지:** 로컬 누끼·흰 배경 합성·문자 검사·결과 저장은 Auto Sourcing의 서버 이미지 잡이 맡는다. 에이전트는 `process-product-image`로 자동 이미지 작업을 제출하거나 반복 조회하지 않는다. `get-image-processing-jobs`로 대상 상품의 상태를 한 번 확인하고 저장된 이미지가 있으면 `get-product-image`로 검토한다. 가공 중이어도 상품명·전체 옵션·상세 설명·카테고리는 독립적으로 편집한다. 이미지에 있는 숫자·치수·주의 문구는 원본에서 확인해 한국어 설명에 보존한다. 저장 직전 상품을 다시 읽어 서버가 바꾼 대표·SKU·상세 이미지 참조를 최신 값으로 병합한다. 이전 이미지 URL로 되돌리거나 SKU 이미지를 비워 공통 사진으로 대신하지 않는다. 이미지 검증은 [이미지 검토와 교정](references/image-quality.md)을 따른다. 글자·제품 변형이 남으면 서버 잡 ID와 검토 결과를 운영자에게 전달한다.
- **상세 설명:** 참고 형식에 맞춰 확인된 안내 → 옵션·규격 비교 → 상세 이미지·설명 순으로 HTML을 구성한다. 대상에 적용되는 근거가 없는 배송 기간·판매자 연락처·보증·반품 조건은 복사하지 않는다. 정적인 요소만 사용하고 스크립트·이벤트 핸들러·외부 폼·추적 요소를 넣지 않는다.
- **카테고리·가격:** 기존 등록 상품의 카테고리와 모든 가격은 유지한다. 신규 상품은 추천 후보와 실제 메타데이터를 원본의 상품 종류·옵션과 대조한다. 필수 고시·인증·조건부 서류의 근거가 부족하면 미확인 항목을 남긴다. 메타정보 조회 성공을 사실 검증이나 업로드 준비 완료로 표현하지 않는다. 가격 변경 요청이 없으면 `confirmPriceChanges`로 확인 절차를 넘기지 않는다.
- **저장:** 최신 대상의 전체 필드와 SKU를 기준으로 변경한 필드만 합쳐 저장한다. 읽지 못한 필드를 빈 값으로 대체하지 않는다. `expectedRevision`을 전달하고 작업 범위 밖의 상품·쇼핑몰 등록을 수정하지 않는다. 참고 상품은 조회 대상으로 둔다.

## 5. VERIFY
- 최종 이미지 목록과 검토 결과를 `processing-review.json`에 남긴다. 실제 PNG/원본을 비교한 뒤에만 `visualPass=true`를 기록한다. 소싱 SKU마다 연결된 최종 이미지와, SKU 이미지가 없는 경우 사용할 실제 대표/상세 컷을 기록한다. `scripts/verify-result.mjs processing-review.json`으로 운영 상품을 재조회하고 SKU·가격·이미지 목록 누락을 검사한다. 이 검사도 육안 검증을 대신하지 않는다.
- `referenceStyle.references`에 선택한 등록 상품의 `productId`, `revision`, `reason`을, `appliedRules`에 실제 적용한 상품명·옵션·상세 규칙을 남긴다. 검증 도우미는 참고 상품의 등록 상태·revision도 다시 확인한다. 빈 옵션·내부 번호·조합 유실·중복 옵션 설명과 흰 배경·중앙 배치 검토 누락은 가공 결함이다. 적합한 사례가 없으면 `referenceStyle.status="no_relevant_reference"`, 전체 조회 여부인 `catalogComplete`, 선택하지 못한 `reason`, 실제 적용한 일반 형식과 빈 `references`를 남긴다. 전체 조회 없이 적합한 사례가 없다고 확정하지 않는다.
- 저장 후 같은 상품을 다시 읽어 상품 ID, revision, 수정한 필드와 보존할 SKU·가격·카테고리·연결 정보를 대조한다.
- 상품명·옵션의 숫자와 단위, SKU 조합, 실제 이미지와 정적 HTML 구조를 확인한다.
- 원본 SKU별 구매·사용 제한과 저장한 표현을 다시 대조한다. 저장 응답의 `stage=ready`만으로 크롭·필수 속성·고시 근거가 완료됐다고 판단하지 않는다. 작업에서 UI 검증을 요청하지 않았으면 저장 API 재조회로 검증한다.
- 원본 기반 processing 초안은 발견된 검증 도구도 호출하고 category/crop 상태와 blocking issue를 그대로 보고한다. 공통 상품 저장 성공이 업로드 준비·쇼핑몰 반영을 뜻하지 않는다.
- 실제 확인한 범위를 구분한다: 초안 제안 / 로컬 저장 / 브라우저 확인 / 이미지 편집 / 외부 반영. 결과 없이 완료라고 하지 않는다.
- 서버 이미지 잡 대기 또는 필수 이미지 미처리, 중국어/잔흔/제품 손상, 누락 SKU, 근거 없는 문구, 잘못 연결된 이미지 또는 부적합 카테고리가 남으면 이슈를 `done`으로 바꾸지 않는다. 저장 응답의 `ready`와 완료 보고서를 종료 기준으로 사용하지 않는다. 게시에만 필요한 미확인 사실은 별도 목록으로 남기되, 가공 결함을 그 목록에 숨기지 않는다.

## 6. RECOVER
- 인증·프로젝트 제한·누락 도구·원본 변경·revision 충돌·HTML/이미지 오류를 구분한다. 권한이나 샌드박스를 변경해 우회하지 않는다.
- revision 충돌은 다시 읽고 사용자의 새 편집과 병합한 뒤 최대 한 번 재시도한다. 저장 응답이 불명확하면 재조회부터 하고 성공한 쓰기를 반복하지 않는다.
- 서버 이미지 잡의 `queued/processing`은 텍스트 가공 실패가 아니다. 생성 요청이나 자동 재시도는 서버에 맡긴다. `higgsfield_submission_unknown`은 새 요청으로 재제출하지 않고 잡 ID와 차단 요인을 전달한다. 이미지 확인이 필요한 경우도 운영자에게 기존 잡의 재시도·검토를 인계한다.
- 근거·도구가 부족하면 제안본과 부족한 항목을 작업에 남긴다. 계속 실패하면 해당 작업의 차단 요인과 필요한 입력을 전달한다.

## 7. PERSIST
- 이미지 생성 입력·공급자 요청 ID·재시도 상태는 서버 DB와 이미지 영수증이 원장이다. 이슈에는 대상 상품 ID·관련 이미지 잡 ID·실제 검토·미완료 상태만 기록한다. 과거 에이전트가 시작한 미완료 생성은 운영자가 정확한 최초 입력으로 서버 잡에 인계하며 에이전트가 새 요청을 만들지 않는다.
- 작업 문서·결과물에 대상·참고 상품 ID/revision, 참고 이유, 적용한 형식, 변경 전후, 저장 후 확인, 미완료 항목을 기록한다.
- 이슈의 `result` 문서에는 최신 revision, 저장 후 확인, 원문 제한 대조, 미완료 항목과 첨부 링크를 기록한다. 보고서 첨부·결과물 등록은 Paperclip 절차와 [실행 폴더에서 첨부](references/tools.md#실행-폴더에서-첨부)를 따르고 기존 첨부·이력을 보존한다.
- 로컬 수정본은 기존 상품/초안 저장소에 둔다. 파일 결과물은 Paperclip의 결과물 등록 절차로 전달한다. 자격증명·전체 카탈로그 덤프를 작업 문서에 넣지 않는다.

## 8. HANDOFF
- 대상 상품/초안 링크, 변경 필드, 검증 범위, 보존한 값, 미지원 크롭·카테고리와 다음 작업을 전달한다.
- 쇼핑몰 업로드 큐에 넣는 행위는 별도로 요청된 업로드 작업에서 수행한다. 가공 에이전트가 저장한 결과는 운영자가 같은 상품 편집 화면에서 검토할 수 있어야 한다.
